> 上位规格：[AI Pet 桌宠架构优化与恢复开发门设计](./2026-08-15-ai-pet-desktop-architecture-optimization-design.md)

## 1. 文档目的

阶段 A 的安全止血与阶段 B 的角色恢复代码已经实施，但桌宠尚未满足恢复常规新功能开发的最终条件：

1. 最终代码上的 `verify:desktop` 曾在单元阶段出现一次固定 5000ms 超时，随后同一用例定向运行 1/1、约 1.06 秒通过。定向通过不能把完整门禁改写为通过，也不能证明超时根因。
2. 相对 `c7d951d`，`apps/desktop/tests` 与 `tests/e2e` 合计 `+1956/-1294`，净增 `662` 行。此前机械要求测试与 E2E 总量净减少，但剩余内容包含安全、竞态、持久化与真实 Electron 证据，不能为追求行数删除唯一 owner。
3. 仍需在同一个最终可执行树 HEAD 上取得完整桌宠质量门证据，并确认网站等受保护业务路径零差异。

本设计只关闭以上三项，不继续扩展阶段 C，也不把“所有架构债务清零”设为恢复开发的前提。目标是形成可信、有限、不会无限追加测试或无限重跑的解锁门。

## 2. 已知事实与证据边界

### 2.1 当前已知事实

- `verify:characters` 已在第二轮测试表达减法的最终代码上退出 0，其中 Electron E2E 为 62/62。
- Desktop 定向聚合、Desktop typecheck、Desktop test、security 20/20 和 integration 46/46 已分别取得通过证据。
- `verify:desktop` 的一次完整执行在单元阶段退出 1；失败用例为 `official-default-character.test.ts` 的“损坏索引后重建可写索引并保留有效用户角色、草稿与损坏证据”，达到固定 5000ms。
- 该用例随后唯一一次定向复现退出 0，1/1 通过，约 1.06 秒。
- 当前 Desktop Vitest 配置使用 `maxWorkers: 4`；这只是运行配置事实，不等于已证明 worker 数量是根因。
- 受保护的网站、CloudBase、scanner 和网站 E2E/配置路径在既有验收中零差异。
- 相对 `c7d951d` 的测试与 E2E 精确净值为 `+662`。

### 2.2 不得从事实外推的结论

当前证据不能证明以下任一说法：

- 测试本身一定过慢；
- 生产恢复实现一定存在性能回归；
- 文件系统、CPU、worker 调度或清理竞态中的任何一项已经被确认；
- 提高超时、增加 retry 或降低并行度就是正确修复；
- 剩余 662 行全部必要，或全部可以删除；
- 一次定向通过等价于完整门禁通过。

调查必须先建立能捕获同一超时症状的快速反馈环，再形成根因结论。

## 3. 方案比较与裁决

### 3.1 方案一：根因修复、唯一 owner 裁决、同一最终可执行树全门解锁

先用 `diagnosing-bugs` 建立秒级、可无人值守、能高复现原超时症状的压力反馈环；按 TDD 修复已证实根因。随后枚举相对基线的每个变更测试文件及有效 diff hunk/测试簇，建立最终 owner inventory，继续删除重复表达并逐项登记不可删除的唯一安全证据。最后在同一个最终可执行树 HEAD 执行全部解锁门。

优点：保留验证可信度，不用机械行数牺牲安全证据，且有明确终点。缺点：需要一次受控诊断和 owner 审计。

### 3.2 方案二：继续强制测试总量净负

继续删除直到相对 `c7d951d` 的测试与 E2E 总量为负。

优点：数字简单。缺点：行数不能表达安全价值，极易删除角色导入 token、真实 Store 重启、竞态、证据保留和 Electron 生命周期的唯一证据；也不能解决 `verify:desktop` 不可信的问题。

### 3.3 方案三：接受波动并直接恢复开发

保留现有超时，把定向通过视作足够证据，直接继续新功能。

优点：短期最快。缺点：以后无法区分旧波动与新回归，完整桌面门长期不可信，技术债会重新累积。

### 3.4 最终裁决

采用方案一。方案二违反“不能降低证据”的安全底线；方案三违反上位规格的恢复开发门。方案一的完成标准是可证明的门禁与单一 owner，而不是机械追求负行数。

## 4. 目标与非目标

### 4.1 目标

1. 通过可重复、快速、红能力明确的反馈环定位并修复 `verify:desktop` 并行负载下的 5 秒超时根因。
2. 对 `c7d951d..最终可执行树 HEAD` 的每个变更测试文件及有效 diff hunk/测试簇建立最终唯一 owner inventory，并让逐文件 `numstat` 与 Git 总账完整对账。
3. 删除仍然重复、只服务旧路径或验证同一 seam 同一失败语义的表达。
4. 用“单一 owner、旧路径零引用、测试分层正确、证据不降低”替代机械净负数门。
5. 在同一个最终可执行树 HEAD 上取得全部自动化门退出 0，再以唯一一个纯验收文档后继提交正式记录桌宠可以恢复常规新功能开发。

### 4.2 非目标

- 不实现 C1–C10 中任何新业务能力或大规模结构改造。
- 不顺带优化角色工作室 UI、角色动画、Provider、Agent 工具或网站。
- 不新增通用测试 DSL、第二套 fixture 框架、全仓验证框架或长期诊断服务。
- 不通过提高 timeout、增加 retry、跳过测试、降低断言或移出门禁来取得绿色结果。
- 不以单纯拆文件、改名或移动测试制造“减少”数字。
- 不把 Windows 人工观察伪装成自动化通过。

## 5. 第一段：根治 `verify:desktop` 的并行 5 秒超时

### 5.1 先建立秒级红能力反馈环

实施必须遵循 `diagnosing-bugs`，在阅读实现和选择修复前先建立一条明确命令。该命令应满足：

- **同症状**：经过与完整门等价的并行压力，使目标恢复用例因达到 5000ms 或同一受阻边界而失败；不能用另一种错误代替。
- **红能力**：已实际捕获至少一次目标症状，并输出成功次数、失败次数、单次耗时和最高耗时。
- **高复现**：在固定轮数、固定 worker 与固定输入下达到足以区分修复前后的复现率；不得只等待低概率偶发。
- **快速**：一次反馈循环以秒计，不运行完整 `verify:desktop`，不依赖人工操作。
- **确定**：固定随机种子、临时目录策略和并行压力；相同代码的判定规则一致。
- **可清理**：若需要临时 harness 或诊断日志，必须使用明确的 debug 标识，修复后删除；不得成为第二套永久测试入口。

优先复用现有 Vitest 测试入口和真实 `CharacterStore`/官方默认角色恢复链。只有现有 seam 不能稳定施压时，才允许建立最小临时 harness；不得为了复现而修改生产超时或注入一个产品中不存在的失败。

本轮诊断最多依次使用三个 feedback seam，不得继续发明第四种复现方式：

1. **目标用例压力循环**：固定目标恢复用例、输入、临时目录策略和 worker 数，重复执行并记录每轮耗时与超时率。
2. **同文件或相邻文件系统重测试压力**：只加入 `official-default-character.test.ts` 同文件场景，或 inventory 证明与其争用同类真实文件事务的相邻重测试；不得加入无关 CPU/网络噪声。
3. **Desktop unit 固定负载**：固定文件清单、顺序/种子和 worker 数，以完整 Desktop unit 的真实并行负载作为最宽反馈 seam；仍须单独识别目标用例的同症状失败。

单条命令最多 15 分钟，整个超时调查从第一次压力命令开始最多 60 分钟。最多保留五个假设，每个假设最多执行两个单变量 probe；同一 probe 不得换名字重复运行。达到任一预算即结束本轮诊断。

若三个 seam 均未捕获同症状，或 60 分钟内无法定位根因，本轮终局必须写为“开发门仍关闭”。此时发布脱敏诊断报告，列出每个 seam、命令、轮数、耗时、结果、已排除假设和缺失证据；停止超时代码修改，并转去执行可并行的 owner inventory 审计。后续只有取得新的运行证据或环境条件后，另立一份短规格，才能继续该超时诊断；禁止在本规格下无限换 seam。

### 5.2 候选假设与可证伪预测

以下只是调查开始时的候选假设，不是根因结论。反馈环建立后按证据重新排序，形成 3–5 个最相关假设；每个假设最多两个单变量 probe：

1. **共享文件系统 I/O 竞争**：如果多个文件系统重测试争用临时磁盘是原因，那么保持目标输入不变、只改变等价 I/O 竞争强度，会使目标耗时和失败率随竞争强度单调变化。
2. **目标场景存在可消除的重复磁盘工作**：如果该用例或正式恢复链重复读取、复制或重建同一资源是原因，那么计数/时序探针会显示同一事务内重复工作；删除重复工作后，结果不变且耗时明显下降。
3. **测试清理与并行 worker 生命周期重叠**：如果异步清理未完成或目录生命周期交叉是原因，那么边界探针会观察到前一场景清理与目标场景运行重叠；等待真实 cleanup Promise 或修正 owner 后重叠消失。
4. **CPU 或事件循环拥塞**：如果图片/JSON/哈希等同步工作阻塞 worker 是原因，那么性能测量会出现稳定长任务；隔离该已证实工作后墙钟耗时下降，而单纯改变磁盘压力无明显影响。
5. **进程级共享状态或缓存泄漏**：如果前序测试改变了目标依赖的共享状态，那么固定前序集合会稳定改变结果；清除错误共享 owner 后，执行顺序不再影响耗时和行为。

任何假设只有在其预测被反馈环或单变量探针支持后才能进入修复。未支持的假设应被明确排除，不得在代码中留下“可能有用”的防御性补丁。

### 5.3 TDD 修复顺序

1. 将最小复现固化在正确的公开 seam，先观察 RED。
2. 若现有测试已经直接覆盖该 seam，只增强其可重复压力表达，不再为同一行为新增第二个 owner。
3. 编写只足以消除已证实根因的最小实现；不得顺带重构角色恢复体系。
4. 运行最小回归测试观察 GREEN，再运行原始未缩小反馈环确认原症状消失。
5. 删除全部临时诊断、throwaway harness、debug 日志和只服务错误假设的代码。
6. 运行受影响 package 的定向测试与 typecheck，再进入第三段完整门。

若正确 seam 不存在，先记录这是架构发现，并建立最窄的公开行为 seam；新 seam 必须替代内部耦合测试并删除旧表达，不能形成永久双轨。

### 5.4 明确禁止的伪修复

- 不把 5000ms 改为更大数值。
- 不增加 retry、repeat-until-pass 或失败后自动重跑。
- 不使用 `skip`、`todo`、排除文件或降低断言。
- 不把无证据降低 `maxWorkers` 当作让门禁变绿的手段；并发配置只按第 5.5 节裁决。
- 不把快速定向通过写成完整门通过。
- 不通过提前 return、吞异常或 mock 掉真实文件事务使测试变快。

### 5.5 `maxWorkers` 的限域替代与量化门

本节只在本规格的超时根因调查与恢复开发门范围内，替代关联减法规格第 5.2 节“不得删除 `maxWorkers: 4` 配置”的固定值条款；其余 worker 活性行为测试与验证配置契约继续有效。该替代不授权其他 workspace 调低并发，也不预先认定 4 workers 是根因。

只有同时满足以下测量门，才允许修改 Desktop `maxWorkers`：

1. 在同一压力 loop、同一机器条件和同一输入下，4 workers 五轮中至少两轮出现目标同症状 RED（至少 2/5 红）。
2. 候选 3 workers 或 2 workers 在完全相同的压力 loop 下连续五轮全部 GREEN（5/5 绿）。
3. 若 3 和 2 都满足，选择可稳定通过的最高值 3；若只有 2 满足，才可选择 2。
4. 选定值落盘后，完整 Desktop unit 连续执行两次且均退出 0；两次都记录总耗时、目标用例耗时和 worker 值。
5. 增加或更新验证配置契约测试，锁定经测量的选定值与最低并发边界，并记录相对 4 workers 的总耗时变化。

永久值最低为 2；1 worker 和串行运行不允许作为本规格的永久解法。任一测量条件不满足时，`maxWorkers` 保持 4，不得以“偶尔更稳”修改配置。即使满足量化门，若探针同时证明生产路径存在可消除的重复工作，也应优先删除重复工作并重新以 4 workers 测量，不能用降并发掩盖实现问题。

### 5.6 第一段完成标准

- 有一条已运行的秒级、红能力、高复现反馈命令和脱敏结果记录。
- 3–5 个假设均有支持或排除证据，最终根因可明确陈述。
- 回归测试先 RED 后 GREEN；原始反馈环在修复后 GREEN。
- 没有 timeout、retry、skip、无证据 worker 降级或断言放宽；如并发预算确为根因，已完整满足第 5.5 节量化门。
- 临时诊断和错误方向代码全部清理。

## 6. 第二段：变更测试文件最终唯一 owner inventory 与减法裁决

### 6.1 账本基线

唯一比较基线为 `c7d951d`，范围只包括：

```text
apps/desktop/tests
tests/e2e
```

当前账本为：

| 范围 | 新增 | 删除 | 净值 |
| --- | ---: | ---: | ---: |
| `apps/desktop/tests` | 1648 | 825 | +823 |
| `tests/e2e` | 308 | 469 | -161 |
| 合计 | 1956 | 1294 | +662 |

实施过程中每个减法提交都重新计算精确 `numstat`，但不以“必须降到零或负数”驱动删除。

### 6.2 唯一 owner 的定义

一项测试只有同时满足以下条件，才可登记为唯一 owner：

1. 它在正确的公开 seam 观察业务或安全行为，不依赖生产源码字符串、私有字段或重复实现细节。
2. 删除或破坏对应不变量时，该测试能够 RED；mutation、历史失败或等价可证伪证据必须可追溯。
3. 仓库中没有另一项测试在同一层、以同一输入类别、证明同一成功或失败语义。
4. 它属于最便宜且仍真实的测试层；能由单元/集成可靠证明的内容不重复放入 E2E。
5. 它没有继续服务已删除的 writer、channel、schema、fallback、wrapper 或旧状态权威。

“测试名称不同”“fixture 不同”或“将来可能有用”不能证明唯一性。

### 6.3 Inventory 枚举单位与必填字段

正式 inventory 固定写入 `docs/operations/desktop-test-owner-inventory.md`，作为门禁前提交到最终可执行树 HEAD 的审计文档；关联规格和最终验收只链接该文件，不各自复制一份清单。

Inventory 不把净增 662 行逐行分配给 owner。逐行分配会把上下文、装配和删除混成业务证据，无法可靠复核。唯一合法枚举方法是：

1. 用 Git 取得 `c7d951d..最终可执行树 HEAD` 在 `apps/desktop/tests` 与 `tests/e2e` 下的每一个变更文件。
2. 对每个文件逐个读取有效 diff hunk，并按可独立说明的测试簇登记；同一 hunk 包含两个不变量时拆成两个测试簇，同一测试簇跨相邻 hunk 时可合并但须列出全部 hunk 位置。
3. 每个变更文件必须至少有一条 inventory，或写明可核验的排除理由；不能因文件净减、只删除内容或已在旧报告出现而省略。
4. 每个文件的 added/deleted `numstat` 与 inventory 条目对账；所有文件求和必须与 Git 范围总账完整一致。二进制或无法给出行数的文件必须单独列出并说明，本范围原则上不应出现此类文件。

每个测试簇至少登记：

- 文件路径与有效 diff hunk/测试标题定位；
- 分类：`业务 owner`、`测试装配`、`已删旧路径`、`纯移动/格式` 四选一；混合 hunk 必须拆项；
- 被保护的不变量，或装配/删除/移动的准确目的；
- 公开 seam 与所属测试层；非业务 owner 明确写“不适用”；
- RED 能力证据；非业务 owner 说明由哪个业务测试簇验证装配结果，纯格式则写“不产生行为证据”；
- 相邻/疑似重复 owner 及裁决；
- 是否依赖旧生产路径；
- 保留、合并、下移、替换、删除或排除结论；
- 文件级 added/deleted `numstat` 与对账状态。

四类含义固定如下：

- **业务 owner**：直接证明安全、竞态、持久化、恢复或真实 Electron 行为。
- **测试装配**：fixture、builder、页面发现、依赖 factory 等使业务 owner 可运行但自身不拥有业务不变量的表达。
- **已删旧路径**：相对基线删除且不再有有效运行入口的旧测试、旧 fixture 或旧断言；必须同时给出零引用证据。
- **纯移动/格式**：行为和有效表达均未改变的移动、重排或格式变化；必须用 diff/重命名证据证明，不能借此声明减法收益。

Inventory 是审计证据，不新增运行时代码，也不复制每条断言正文。

### 6.4 必须逐项登记的 owner 类别

至少覆盖：

- 角色包导入 owner token、真实 Store 重启、竞态、证据排他发布/保留、256 项上限与 2000ms 软预算；
- 启动恢复顺序、官方默认角色 fallback、最终 load 瞬时/持续失败、不可变恢复快照；
- Main/Preload Schema 双边界、Pet 异步顺序、Workshop StrictMode 单请求与 RPC 失败脱敏；
- Desktop Electron 生命周期、安全诊断、窗口交互和两条角色恢复真实重启 E2E；
- 上位减法规格已经列明的其余安全、持久化和跨进程证据。

这些类别不是自动保留名单。每个 owner 仍须满足第 6.2 节；发现同义重复时继续做减法。

### 6.5 测试分层裁决

- 纯函数、Schema 与单模块状态规则由 package 单元测试拥有。
- 真实文件事务、跨模块组合和恢复边界由 Desktop 组合或根 integration 拥有。
- Preload/Main 两侧各自的运行时 Schema 边界可以分别拥有一个代表非法值，但同一侧不重复枚举同义输入。
- Electron E2E 只保留必须经过真实窗口、进程重启、Preload 或操作系统文件身份才能证明的纵向场景。
- E2E 不重复单元层已经完整拥有的矩阵；单元层不通过复制 E2E 页面流程证明自身实现。

### 6.6 删除门

删除或合并前必须完成：

1. 指出被删表达的替代 owner 与准确 seam。
2. 用 mutation、历史 RED 或最小破坏证明替代 owner 会捕获回归。
3. 确认被删项不是唯一安全、竞态、持久化或真实 Electron 证据。
4. 先使保留 owner GREEN，再删除旧测试、旧 helper、旧 fixture 和只服务旧路径的注释。
5. 运行受影响层的定向测试、typecheck 与 `git diff --check`。

不得创建新的通用 helper 只为少量行数减法；新增抽象必须使 owner 数和总代码同时减少。若审计发现需要删除大量文件，仍须按仓库规则列出精确目标、恢复方式并取得二次明确批准；本规格不预先授权未列明的大量文件删除。

### 6.7 对旧机械行数门的替代

本规格在“恢复常规开发门”范围内，明确替代关联减法规格第 9 节“测试总量应相对 `c7d951d` 净减少”的机械完成条件。新的完成条件为：

1. 每项新增证据只有一个经登记 owner；
2. 已替代的生产旧路径、旧测试入口与只服务旧实现的 fixture/helper 零引用；
3. 测试位于能够真实证明行为的最低合理层；
4. 重复表达已删除，最终净值如实记录；
5. 安全、竞态、持久化和真实 Electron 证据不降低；
6. 独立审查的 Critical/Important 为零。

这不是放宽质量要求。即使最终仍为净增，只要每一部分均有唯一 owner 与 RED 能力，它就是新安全能力的可解释成本；反之，即使净值为负，只要仍有双 owner、旧路径或证据缺口，也不得完成。

### 6.8 第二段完成标准

- `c7d951d..最终可执行树 HEAD` 下每个变更测试文件及其有效 diff hunk/测试簇都已有条目或可核验排除理由；不把 662 行逐行分配给 owner。
- 逐文件 added/deleted `numstat` 与 Git 范围总账完整对账，最终净值如实记录。
- 所有可安全删除的重复表达已删除，且没有用新 helper 抵消减法。
- 所有保留 owner 都有 seam、层级和 RED 能力证据。
- 旧生产符号、旧测试入口和旧 fixture/helper 扫描零命中。
- 不宣称“安全减法已穷尽”，也不把本次 inventory 外推为未来不再存在新的安全减法机会。

## 7. 第三段：同一最终可执行树 HEAD 的正式解锁门

### 7.1 自动化命令

“最终可执行树 HEAD”是第一、二段全部代码、测试、fixture、脚本、依赖、`package.json`、锁文件和可执行配置已经提交，且此后不再改变这些内容的提交。规格、计划与 inventory 应在门禁前同步到该 HEAD。按根 `package.json` 当前脚本运行：

```powershell
pnpm.cmd verify:desktop
pnpm.cmd verify:characters
pnpm.cmd verify:behavior
pnpm.cmd test:security
pnpm.cmd test:integration
```

五条顶层命令必须全部实际执行并退出 0。脚本内部重复测试属于当前质量门契约，不因耗时而删减。历史绿色、另一可执行树 HEAD 的绿色、定向绿色或某条 verify 内嵌的相同步骤，均不能替代这五条最终记录。

五门通过后，允许且只允许一个后继提交，专门更新纯验收文档、状态摘要及其相互链接。该提交不得修改 `apps/`、`packages/`、`tests/`、根 `package.json`、锁文件、测试配置、构建配置或任何可执行脚本；提交前后必须用 Git diff 列出文件并证明上述可执行范围零差异。因为可执行树没有变化，该唯一纯验收文档提交不要求重新运行五条长门。若门后出现第二个文档提交或任一可执行差异，原解锁证据失效，必须先整理成新的最终可执行树 HEAD 并重新执行五门。

### 7.2 15 分钟硬停与失败处理

- 每条顶层命令达到 15 分钟立即终止，记录最后阶段和已观察结果，不能继续等待。
- 任一命令退出非零，解锁保持关闭；不连续重跑完整门碰运气。
- 对失败只建立新的最小反馈环并按第一段方法诊断；修复后产生新的最终可执行树 HEAD，五条解锁命令必须在该 HEAD 重新执行。
- 基础设施或环境失败与产品失败分开记录，但两者都不能被写成退出 0。
- 不修改 timeout、retry、测试范围或无证据降低 worker 来绕过失败；并发配置只有满足第 5.5 节量化门时才可调整。

### 7.3 受保护路径与差异检查

最终必须确认以下路径相对实施基线、工作树和暂存区均零差异：

```text
apps/website
apps/cloudbase-api
apps/package-scanner
cloudbase
tests/e2e/website.spec.ts
tests/playwright.website.config.ts
```

在最终可执行树 HEAD 上执行并记录：

- 最终 `git diff --check`；
- 工作树状态；
- 旧 owner/旧入口零引用扫描；
- 相对 `c7d951d` 的最终测试与 E2E 精确 `numstat`。

唯一纯验收文档后继提交还须记录 `最终可执行树 HEAD..验收文档 HEAD` 的路径差异，证明只有第 9.1 节指定文档变化，且所有可执行范围零差异。

不得运行或修改网站业务来“顺便验证”。保护路径只做只读差异检查。

### 7.4 Windows 人工验收

真实窗口层级、焦点、布局、文案可读性、重启视觉、拖拽、托盘和资源释放等无法由当前自动化证明的项目，按影响范围记录为“待用户人工确认”。

人工待验不阻止与这些行为无关的常规功能开发；后续新功能若直接触及某个人工待验行为，必须在该功能交付前完成对应人工验收。不得把“待用户人工确认”写成通过。

## 8. 数据、日志与隐私

- 压力环和诊断日志使用临时目录与合成角色数据，不读取用户真实角色目录。
- 日志不得包含完整绝对路径、文件正文、损坏 marker 原字节、owner token、哈希、API Key、Authorization 或 Provider 私有响应。
- 需要展示路径时只保留固定测试标识或使用 `<REDACTED>`。
- 临时性能计数只记录阶段名、耗时、次数和失败类别，不记录业务正文。
- 所有 `[DEBUG-*]` 日志、性能探针和 throwaway harness 在修复后删除；正式日志契约不得因诊断扩大。
- Inventory 记录不变量和 owner，不复制敏感 fixture 内容。

## 9. 提交、复审与恢复

### 9.1 小步提交

实现与减法分别使用小提交：

1. 反馈环与最小根因修复；
2. owner inventory 驱动的替换式减法；
3. 门禁前的规格、计划、inventory 与替代关系同步。

每个实现任务执行 TDD，并由独立子智能体复审。Critical/Important 未清零时不得进入下一段。不得让多个子智能体同时修改同一文件。

五门通过后，只允许第 7.1 节定义的一个纯验收文档后继提交。该提交必须同步更新：

- `docs/superpowers/specs/2026-08-20-desktop-code-subtraction-design.md`：写明本规格替代第 5.2 节固定 worker 值与第 9 节机械净负数门的准确范围、生效的最终可执行树 HEAD、[最终 inventory](../../operations/desktop-test-owner-inventory.md) 链接和精确 Git 总账；未触及条款继续有效。
- `docs/operations/character-workshop-acceptance.md`：记录五条命令、退出码、耗时、最终可执行树 HEAD、Windows 人工待验项及解锁结论。
- `docs/superpowers/specs/2026-08-15-ai-pet-desktop-architecture-optimization-design.md`：只更新恢复常规功能开发门的状态摘要，链接本规格、inventory 与验收记录，不复制详细命令日志。

三处必须在同一纯验收文档提交中交叉链接，并使用同一最终可执行树 HEAD 和验收文档 HEAD。不得只更新本规格形成两个有效事实源；顶端状态、正文历史结论与当前摘要冲突时，必须明确标注历史适用提交和新替代关系。

### 9.2 失败恢复

- 每个删除任务可由其独立 Git 提交恢复，不使用破坏性 reset。
- 修复使行为或性能退化时，回到最后一个已验证的小提交重新设计，不在错误方向继续叠补丁。
- 单点调查、命令或审查超过 15 分钟仍未收敛时，立即停止该做法；超时调查只能在第 5.1 节三个 seam 与 60 分钟总预算内切换。
- 如果在预算内无法建立红能力反馈环或定位根因，则执行第 5.1 节终局：开发门保持关闭、发布脱敏诊断报告、转去 owner inventory，并等待新证据与新的短规格；不能凭推测提交修复。

## 10. 正式解锁标准

只有以下条件同时满足，才可在验收记录中写“桌宠恢复常规新功能开发”：

1. 5 秒超时存在秒级红能力反馈环，根因经可证伪证据确认并以 TDD 修复。
2. 修复未提高 timeout、未增加 retry、未跳过测试、未无证据降低并行配置或安全断言；如调整并发预算，已完整满足第 5.5 节量化门。
3. `c7d951d..最终可执行树 HEAD` 的每个变更测试文件与有效 diff hunk/测试簇均完成 inventory；逐文件 `numstat` 与 Git 总账对齐，重复表达和旧路径已删除。
4. 最终精确净值已记录；保留的业务 owner 具有正确 seam、分层和 RED 能力，测试装配、已删旧路径与纯移动/格式均已单独分类。
5. 同一个最终可执行树 HEAD 上的 `verify:desktop`、`verify:characters`、`verify:behavior`、`test:security`、`test:integration` 全部退出 0。
6. 受保护的网站、CloudBase、scanner、cloudbase 与网站 E2E/配置路径零差异。
7. `git diff --check` 通过，工作树无本任务遗留，临时诊断全部删除。
8. 独立规格审查与代码质量审查的 Critical/Important 均为零。
9. 未自动化的 Windows 项按影响范围明确记录为“待用户人工确认”。
10. 唯一纯验收文档后继提交已同步三处事实源，并用 Git diff 证明相对最终可执行树 HEAD 的可执行范围零差异。

任一条件未满足，状态只能写“开发门仍关闭”并说明下一步，不能用等价证据、风险接受或历史通过替代。

## 11. 解锁后的 C1–C10 触达规则

解锁不表示阶段 C 和 D 债务已经清零。恢复常规开发后，普通功能可以继续，但新功能触及下列区域时，必须先完成或与功能同一纵向切片完成对应治理：

| 触及区域 | 前置治理 |
| --- | --- |
| Provider 设置保存、配置 reset 与失败补偿 | C1 设置 mutation 单一权威 |
| compiled 角色写入、旧格式恢复或 writer 选择 | C2 compiled writer 与 legacy recovery 裁决 |
| 角色 source 安装、catalog 或导入事务 | C3 source 安装收口 |
| 新增大量测试、内部测试入口或跨层重复矩阵 | C4 测试接缝治理 |
| 角色工作室编辑、自动保存、编译、flush 或关闭状态 | C5 工作室深模块 |
| 角色激活、播放器组合、动作协调或统一关闭 | C6 角色运行组合 |
| 新增或修改 IPC 契约 | C7 IPC 契约试点或已验证模式 |
| 角色动作选择、V1/V2 投影或 Main/Renderer 双权威 | C8 Main 单一动作权威 |
| 聊天窗口销毁重建后的展示恢复 | C9 可选展示快照；只有产品需求明确时实施 |
| Provider fallback、跨 Provider 重放或设置承诺 | C10 Provider fallback 诚实化 |

每个 C 切片同时执行阶段 D：新权威通过后删除旧 writer、旧 channel、旧 selector、旧 recovery、旧 Schema owner 和只服务旧实现的测试。不得因为开发门已经解锁而重新叠加永久双轨。
