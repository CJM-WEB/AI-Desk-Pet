# AI 桌宠产品全局设计与演进计划

> 文档状态：已确认的全局粗设计  
> 产品代号：`Myself`  
> 目标平台：Windows 10/11  
> 首批用户：产品负责人及 5–20 名邀请测试者  
> 基准日期：2026-07-20  
> 详细落地规格：[第一阶段端到端 MVP 开发规格](./2026-07-20-phase-1-mvp-development-design.md)

## 1. 文档目的

本文汇总当前已经确认的产品方向、架构边界、路线选择和长期演进计划，作为后续细化各阶段设计时的上层约束。它不是逐任务实施清单；第一阶段的可执行设计由配套的 MVP 开发规格负责。

当后续需求发生变化时，应按以下顺序维护：

1. 先记录为什么需要改变。
2. 更新受影响的架构决策与阶段目标。
3. 更新对应阶段的详细规格和验收标准。
4. 最后修改实现计划和代码。

## 2. 产品愿景

`Myself` 是一只常驻 Windows 桌面的 2D AI 桌宠。它既具有陪伴感，也能通过自然语言在用户明确授权的目录中完成安全、简单、可解释的文件操作。

产品的长期差异化不依赖“模型比别人更聪明”，而来自以下组合：

- 桌面角色带来的持续存在感和清晰状态反馈。
- 用户可自行选择 OpenAI 兼容模型与服务提供方。
- 本地受控 Agent 工具，而不是把整台电脑权限交给模型。
- 每个写操作都可预览、确认、取消和审计。
- 桌宠角色、模型、工具和网站视觉能够独立演进。

## 3. 已确认的产品原则

### 3.1 快速形成真实闭环

第一版必须是可以实际安装、配置、授权目录并完成文件任务的纵向产品切片。只搭建工程脚手架、只制作角色动画或只做聊天界面，都不能算 MVP 落地。

### 3.2 默认安全而非默认全能

- 只访问用户主动选择的授权目录。
- 不向模型暴露 Shell、PowerShell 或任意系统执行能力。
- 所有模型工具调用必须经过本地结构校验和权限策略。
- 第一阶段所有写操作都先预览并确认。
- 不静默覆盖已有文件。
- 崩溃重启后不自动恢复未执行的写操作。

### 3.3 自带密钥，自由换模型

普通用户只需选择预置的模型提供商和模型，并填写自己的 API Key；Base URL、协议类型和能力标签由内置模型目录管理。预置范围覆盖 OpenAI、Anthropic、Gemini、DeepSeek、Kimi、通义千问、智谱、豆包、腾讯混元、MiniMax 等国内外主流服务。

高级设置保留自定义 Provider，可填写 Base URL、模型 ID、协议类型和受限额外参数。客户端通过 Provider Adapter 隔离 OpenAI 兼容、Anthropic 和 Gemini 等协议差异，不建设统一模型额度或计费后端。

### 3.4 轻首版、可扩展边界

首版不提前实现账号、云同步、订阅、角色商店、语音、视觉识别和高级自主 Agent，但相关领域必须有明确边界，避免以后只能推倒重写。

### 3.5 官网先可信，再炫酷

首版官网的首要目标是解释产品、安全边界和安装方法，并提供可信下载。后续可以加入 Motion、GSAP、Rive 和 Three.js 等高级动效，但动效不能阻塞下载、阅读或无障碍访问。

## 4. 已确认的技术路线

### 4.1 桌面客户端

- Electron：透明窗口、置顶、托盘、快捷键和 Windows 打包。
- React + TypeScript：桌宠气泡、确认卡片、设置界面。
- Vite：开发和构建。
- Electron 主进程：模型调用、受控文件工具、敏感数据和窗口管理。
- Electron preload：暴露最小化、强类型、白名单 IPC。
- Electron `safeStorage`：加密 API Key。
- NSIS：生成 Windows 安装程序。

选择 Electron 的原因是开发速度、Windows 桌面能力和全 TypeScript 工具链。其安装包与内存占用高于 Tauri，但这不是邀请测试阶段的首要风险。

### 4.2 官网

- 官网使用 Next.js + React + TypeScript。
- 首版静态导出，不建设网站后端。
- 腾讯云对象存储与 CDN 承载静态站点、版本清单和安装包。
- 用户已有腾讯云备案域名；具体域名属于部署配置，不写死在业务代码中。

### 4.3 共享工程

- pnpm workspace 管理 monorepo。
- 共享类型、Agent Core、文件工具、角色运行时和设计变量拆成独立 package。
- 首版不引入大型 Agent 框架，由轻量 Agent Orchestrator 管理模型轮次、工具请求、确认和结果。

## 5. 目标系统架构

```text
用户
  │
  ▼
Electron Renderer
  ├─ 透明桌宠窗口
  ├─ 对话气泡与确认卡片
  ├─ 设置窗口
  └─ 角色状态机
  │  仅允许白名单 IPC
  ▼
Electron Main（可信本地核心）
  ├─ Agent Orchestrator
  ├─ Provider Registry / Model Router
  ├─ Tool Registry / MCP Client
  ├─ Permission Policy
  ├─ Context Disclosure / Local Memory
  ├─ File Tool Service
  ├─ Secret / Settings Store
  └─ Audit Writer
      │                  │
      ▼                  ▼
兼容模型 API       用户授权目录

独立 Next.js 官网
  └─ 静态导出 → 腾讯云对象存储/CDN → 已备案域名
```

模型可以提出结构化工具请求，但不能直接访问文件系统。真正的路径解析、权限判断、冲突检查和执行都发生在 Electron 主进程。

## 6. 长期产品范围

### 6.1 计划逐步支持

- 可替换的 2D 角色包与更多动画状态。
- 国内外预置模型目录、多个配置档案、高级自定义 Provider 和按能力路由。
- 内置 MCP 与用户添加的 `stdio`、HTTP MCP 服务。
- 被动、辅助和自主三级 Agent 主动性，默认辅助模式。
- 授权目录内的查看、搜索、新建、复制、移动、重命名和回收站删除。
- 桌宠进入文件夹、绑定资源管理器内容区、托盘呼唤和召回桌面。
- 任务预览、确认、取消、结果反馈和有限审计。
- 更完善的安装、版本发布、自动更新和代码签名。
- 高级动效官网、角色展示和后续社区能力。
- 经过独立设计后增加语音、应用工具或本地模型。

### 6.2 当前全局非目标

- 训练自有基础模型。
- 允许模型直接执行 Shell 或任意代码。
- 默认访问整台电脑。
- 无人值守的后台自主任务。
- 在未建立权限、风控和恢复设计前控制应用或浏览器。
- 首版账号、云同步、订阅支付和统一模型额度。

## 7. 分阶段路线图

### 阶段 1：端到端可演示 MVP

目标：用最小功能集证明“桌宠形态 + 可换模型 + 安全文件 Agent”能够形成真实使用闭环。

包含：

- Windows 透明桌宠，可拖动、置顶并从托盘控制。
- 点击桌宠弹出聊天气泡。
- 一个 OpenAI 兼容模型配置。
- 一个用户授权目录。
- 查看目录、读取受限文本、新建空文件/文件夹、重命名文件/文件夹。
- 所有写操作预览、确认和禁止覆盖。
- 待机、聆听、思考、执行、成功、失败六种角色状态。
- 本地可运行的官网首页。
- 可安装的未签名 Windows 开发版。

详细设计见配套的第一阶段规格。

### 阶段 2：完整基础文件 Agent

在阶段 1 的安全模型上增加：

- 多模型配置档案与切换。
- 普通模式的提供商、模型和 API Key 选择，以及高级自定义 Provider。
- 对话、Agent、视觉和备用模型路由；跨提供商故障转移必须预先授权。
- 搜索、复制、移动和回收站删除。
- 更完善的任务历史、错误恢复和设置管理。
- 对 OpenAI 兼容、Anthropic、Gemini 及中国主流模型服务的契约测试。
- 角色资源包加载与至少一个可替换角色示例。

阶段 2 不增加 Shell、静默覆盖和后台自主执行。

### 阶段 3：邀请测试版与公开准备

- 将官网和安装包部署到腾讯云。
- 绑定已备案域名。
- 提供版本清单、SHA-256、安装说明和隐私说明。
- 保留最近三个已验证测试版本并形成回滚流程。
- 建立匿名或用户主动提交的反馈渠道。
- 完成干净 Windows 环境安装、卸载和数据清理验证。
- 根据测试者反馈决定代码签名和自动更新的优先级。

### 阶段 4：体验增强与高级官网

- Motion 或 GSAP 微交互、页面转场和滚动叙事。
- Rive 交互角色演示。
- 按设备能力加载 Three.js 粒子或 3D 场景。
- 全程支持 `prefers-reduced-motion` 与媒体懒加载。
- 根据验证结果扩展语音、角色系统或本地模型。

### 阶段 5：平台化评估

只有在活跃用户、留存和安全数据证明有必要后，才评估：

- 账号与云同步。
- 角色或工具商店。
- 订阅、模型额度和支付。
- 团队管理能力。
- 内置与用户添加的 MCP 服务管理、逐项权限和审计。

资源管理器文件夹空间属于独立 Windows 能力，在基础角色运行时和权限系统稳定后实施。详细设计见：

- [多模型、Agent 与 MCP 系统设计](./2026-07-27-multi-provider-agent-mcp-design.md)
- [文件夹空间与资源管理器图层设计](./2026-07-27-explorer-pet-space-design.md)

## 8. 文件操作的长期安全模型

### 8.1 授权边界

- 用户通过系统目录选择器授权根目录。
- 模型只看到根目录内的相对路径。
- 每次工具执行都重新规范化路径，不能依赖先前验证结果。
- 现有源路径使用真实路径校验；新目标使用已存在父目录的真实路径校验。
- 拒绝 `..` 穿越、绝对路径注入、符号链接或 Junction 逃逸。

### 8.2 风险等级

- 低风险：列目录、搜索、读取受限文本；授权目录内可直接执行。
- 中风险：新建、复制、移动、重命名；展示准确路径后确认。
- 高风险：删除；醒目二次确认并进入 Windows 回收站。

### 8.3 数据最小化

- 文件列表和路径处理在本地完成。
- 只有完成用户请求确有必要时，相关文本才进入模型上下文。
- 文本读取具有类型和大小限制；二进制只提供元数据。
- 日志不记录 API Key、Authorization Header、完整文件内容和完整绝对路径。

## 9. 官网与发布策略

首版官网使用单页结构：

1. 产品定位、桌宠演示和下载按钮。
2. 文件能力与模型切换说明。
3. 授权目录、确认流程和隐私边界。
4. 版本、文件大小、校验和与安装提示。
5. FAQ、隐私说明和反馈入口。

首版发布步骤：

1. 本地构建 NSIS 安装包。
2. 生成版本、大小、SHA-256、发布时间和下载路径组成的版本清单。
3. 在干净 Windows 环境进行冒烟验收。
4. 上传静态网站、版本清单和安装包。
5. 官网只切换到已经验证的版本。

## 10. 质量策略

### 10.1 自动测试层级

- 单元测试：路径守卫、风险分级、Schema、Provider 解析、角色状态机。
- 集成测试：IPC、设置存储、模型 Mock、文件工具与确认状态机。
- 安全测试：路径穿越、Junction、竞态覆盖、提示注入和敏感信息泄露。
- 端到端测试：首次启动、模型配置、授权目录和完整任务流程。
- 官网测试：响应式、下载链接、版本清单和无动效模式。

### 10.2 人工验收

- 干净 Windows 环境安装、启动、托盘、退出和卸载。
- 未签名安装提示与文档一致。
- 授权目录外的操作全部拒绝。
- 取消写操作后文件系统无变化。
- API Key 不出现在普通配置、日志和错误消息中。
- 官网下载文件与展示的 SHA-256 一致。

## 11. 工作流与分工边界

- WS1 工程基础：workspace、构建、共享类型和 IPC 契约。
- WS2 桌宠体验：窗口、气泡、托盘和角色状态机。
- WS3 Agent 与模型：Provider Adapter、工具循环、超时和取消。
- WS4 文件安全：授权、路径守卫、文件工具和安全测试。
- WS5 官网与发布：首页、版本清单、安装说明和腾讯云流程。
- WS6 质量保障：自动化测试、发布验收和回归清单。

WS1 先冻结公共契约。随后 WS2、WS3、WS4 和 WS5 可在不修改彼此内部实现的前提下并行。WS6 从每个工作流开始时就参与，不作为最后补测试的独立尾声。

## 12. 主要风险与控制措施

| 风险 | 影响 | 当前控制措施 |
|---|---|---|
| 兼容模型不支持稳定工具调用 | Agent 无法执行任务 | Provider 契约测试；明确错误；允许更换模型 |
| 模型产生危险或错误路径 | 文件被误操作 | 相对路径、Schema、真实路径校验、写操作确认 |
| Windows Junction 逃逸 | 越过授权目录 | 源路径与目标父目录真实路径校验；安全测试 |
| Electron Renderer 被注入 | 获取本地能力 | 禁用 Node 集成、启用隔离、最小化 preload IPC |
| API Key 泄露 | 用户资产风险 | `safeStorage`、日志脱敏、Renderer 不持有明文密钥 |
| 未签名安装包降低信任 | 测试者放弃安装 | 官网解释、校验和、邀请测试、后续评估签名 |
| 过早追求高级网站 | 延迟核心产品验证 | 首版静态站；高级动效独立阶段实现 |
| 功能范围持续扩张 | MVP 无法完成 | 阶段门禁；新增需求先进入后续路线图 |

## 13. 全局成功信号

第一阶段成功不以下载量衡量，而以闭环是否可靠为准：

- 新用户能在五分钟内完成模型配置、目录授权和首次文件任务。
- 用户能理解桌宠即将执行的动作，并能安全取消。
- 错误时文件系统保持可解释状态。
- 至少两个兼容模型服务通过后续契约验证。
- 邀请测试者愿意在真实目录中重复使用，而不只是体验一次动画。

公开发布前再增加稳定性、安装成功率、任务成功率、留存和反馈指标。

## 14. 架构决策摘要

1. 使用 Electron + React/Vite，而不是 Tauri 或 PySide6，以首版速度优先。
2. 使用 Next.js 静态官网，为未来高级视觉和动态能力保留升级路径。
3. Agent Core 自研最小循环，不引入大型 Agent 框架。
4. 模型只提出工具请求，本地可信主进程拥有最终执行权。
5. 首版自带密钥，不建设统一 AI 后端。
6. 首版未签名、面向邀请测试者，不直接大规模公开分发。
7. 先完成端到端 MVP，再扩充完整文件工具与高级网站。

## 15. 文档治理

- 本文是全局方向与阶段边界的基准。
- 每个阶段有独立详细规格，明确需求编号和验收标准。
- 实施计划必须引用详细规格中的需求编号。
- 架构改变通过 ADR 记录原因、替代方案和影响。
- 代码行为与文档冲突时，不默认代码正确；先确认产品决策，再同步两者。
- 产品正式命名在公开发布准备阶段由产品负责人选择；此前仓库、包名和示例统一使用代号 `Myself`。
