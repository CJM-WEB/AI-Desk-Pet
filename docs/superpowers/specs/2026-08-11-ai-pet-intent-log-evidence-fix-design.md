# 文件意图门与日志证据第二轮修复设计

## 1. 目标

在不改变 Renderer 输入接口、文件授权链和默认聊天原则的前提下，解决最终复审留下的两项阻断问题：

1. 文件意图门仍会漏判常见中英文礼貌执行请求，并会把裸域名、版本号或紧邻知识后缀的讨论误升为文件任务。
2. Electron 测试夹具在日志截断和滚动缓存后才检查哨兵，可能漏掉早期、超长或跨块的敏感信息泄漏。

本轮不新增长期记忆、截图、剪贴板、主动性或其他桌宠功能，不修改、构建、启动或测试网站。

## 2. 约束与不变量

- Main 进程的确定性规则仍是聊天与文件任务的唯一分流权威。
- 普通输入默认聊天；只有“文件操作、合法本地目标、实际执行语气”三项证据同时成立才进入文件任务。
- Renderer 仍只提交自然文本，不增加路由、Provider、权限或路径字段。
- 文件任务继续复用既有授权根、相对路径约束、历史披露、写入确认、重置和迟到事件隔离。
- 不使用模型判断权限方向，不增加 DeepSeek 特例，不因测试抖动放宽无关测试超时。
- 日志测试只持久化布尔命中或稳定类别，不持久化用户正文、Provider 回复、文件正文、密钥或绝对路径。
- 所有新增文档、注释和测试名称使用中文；代码标识符沿用项目英文风格。

## 3. 文件意图门设计

### 3.1 总体流程

`ExplicitFileIntentGate` 保持纯函数式公开接口，内部按以下固定顺序处理：

1. Unicode 归一化与空白规整。
2. 标记引用、翻译对象和远程资源片段，避免其中的操作词参与执行判断。
3. 在操作表达附近提取候选本地文件对象，并为已确认的对象建立受保护片段。
4. 只在受保护文件对象之外判断否定、解释、定义、原因询问、教程和翻译等元语言。
5. 独立计算文件操作、合法本地目标、实际执行语气三项证据；三项均成立才返回 `file_task`，否则返回 `chat`。

返回值继续只包含 `kind`，不携带正文、路径或推断详情。

### 3.2 合法本地目标

允许以下目标形态：

- 相对路径：`.\drafts`、`..\archive`、`./drafts`、`../archive`。
- 带目录分隔符的本地路径片段。
- 常见文件名：`a.txt`、`pyproject.toml`、`不要删除.txt`，不依赖固定扩展名白名单。
- 明确目录指代：`当前文件夹`、`这个目录` 等既有受支持表达。

以下内容必须排除：

- 带协议 URL、`www.` 裸域名和域名路径。
- 邮箱地址。
- 纯数字小数或版本号，例如 `1.2`、`2.0.1`。
- 仅因包含点号而形成、但没有本地文件结构证据的普通 token。

候选目标必须与文件操作处于同一执行结构中；不得用全句任意点号 token 作为文件对象。

### 3.3 实际执行语气

支持以下常见执行结构：

- 中文直接祈使：`读取 a.txt`、`列出 .\drafts`。
- 中文礼貌请求：`请把 …`、`帮我把 …`、`你能帮我 … 吗`。
- 英文直接祈使：`read …`、`delete …`。
- 英文礼貌请求：`Can/Could/Would you please …`。

以下结构默认聊天：

- 定义与功能讨论：`是什么意思`、`是什么功能`。
- 原因与故障讨论：`为什么失败`。
- 教程与方法询问：`如何`、`how to`。
- 引用与翻译：`把“删除 a.txt”这句话翻译成英文`。
- 否定执行：`不要删除 a.txt`。

否定词和知识词只在已识别文件对象片段之外生效，因此 `读取 不要删除.txt` 不会被误判为否定请求。

### 3.4 代表性验收矩阵

必须进入文件任务：

- `请把 report.md 重命名为 archive.md`
- `帮我把 report.md 重命名为 archive.md`
- `你能帮我读取 a.txt 吗？`
- `Can you please delete a.txt?`
- `列出 .\drafts`
- `读取 pyproject.toml`
- `读取 不要删除.txt`

必须保持聊天：

- `读取 a.txt是什么意思？`
- `读取 a.txt为什么失败？`
- `搜索文件是什么功能？`
- `把“删除 a.txt”这句话翻译成英文`
- `read https://example.com/manual.pdf`
- `read www.example.com/manual.pdf`
- `delete user@example.com`
- `Can you delete version 1.2?`

## 4. 日志证据设计

### 4.1 采集时不可逆累计

测试夹具在接收每个原始日志块时、执行截断和滚动缓存之前，立即更新 `CapturedLogEvidence`。每个已配置哨兵只保存布尔命中状态；一旦为 `true`，后续日志不能把它恢复为 `false`。

这样可以覆盖：

- 哨兵位于单个日志块第 4001 字符以后。
- 早期泄漏后来被最近 100 条缓存驱逐。
- 测试结束前公开日志已经完成脱敏。

### 4.2 跨块匹配

日志流可能把一个敏感字符串拆成两个块。夹具为每个流仅保留一个有界尾部，长度为“最长哨兵长度减一”，并使用“上一块尾部 + 当前完整块”做匹配。

尾部只存在于测试进程内，不写入报告；关闭夹具时清空。它不保存完整日志历史。

### 4.3 证据类型

测试为每个敏感类别配置稳定标签，例如：

- 用户输入。
- Provider 回复。
- 文件请求与文件回复。
- API key。
- 授权根。
- Authorization 头。

Authorization 检测同时覆盖普通头格式与 JSON 字段格式，匹配不区分大小写。

### 4.4 公开日志脱敏

处理顺序固定为：

1. 用完整原始块更新布尔证据。
2. 更新跨块有界尾部。
3. 对公开日志执行脱敏和长度限制。
4. 只把脱敏后的日志交给测试诊断或失败报告。

Provider 回复哨兵不再依赖 `additionalSecrets` 来证明“未泄漏”；即使公开日志为安全展示而被脱敏，原始边界的布尔证据仍能发现泄漏。

不增加任何生产 preload 接口。

## 5. 错误与生命周期

- 意图门无法确认任一证据时返回聊天，不抛出错误，也不启动文件授权链。
- 日志证据匹配器只用于测试，不影响应用启动和退出。
- 空哨兵被配置时应立即拒绝测试配置，避免恒真匹配。
- 夹具关闭后不再接受日志块，并清空跨块尾部；已返回的证据为只读快照。
- 受控日志泄漏变异必须在同一 TDD 切片内恢复，并用生产文件零差异检查证明恢复。

## 6. TDD 与验证

### 6.1 文件意图门

按垂直切片依次取得 RED 和 GREEN：

1. 中英文礼貌执行请求。
2. 紧邻文件名的定义、原因询问。
3. 裸域名、邮箱和版本号排除。
4. 既有全部正反例回归及三项证据变异检查。

### 6.2 日志证据

依次覆盖：

1. 单块 4000 字符之后的哨兵。
2. 超过 100 个后续块后仍保留早期命中。
3. 哨兵跨两个日志块。
4. 普通与 JSON Authorization 表达。
5. 受控生产泄漏使新证据 RED，恢复后 GREEN。

### 6.3 门禁

修复完成后顺序运行：

- Gate、日志夹具和命名 Electron 场景聚焦测试。
- Desktop typecheck。
- Security 与 integration。
- 完整 Desktop E2E。
- 在没有其他测试进程竞争时单独运行一次 `verify:behavior`。
- `git diff --check`、网站零差异和本 worktree 进程残留扫描。

如果 `verify:behavior` 仍只因未修改测试的并发固定超时失败，不修改无关测试或全局超时；保存精确证据并作为独立测试基础设施问题报告。任何本轮修改覆盖的测试失败都属于阻断。

## 7. 审查与交付

- 一个实现子智能体负责本轮全部修改，避免共享文件冲突。
- 实现后分别做规格轴与质量轴审查；Critical 或 Important 必须有对应 RED 后再修复。
- 报告更新真实提交哈希、门禁结果和已恢复的受控变异，不得把失败门写成通过。
- 最终提交只包含智能桌宠代码、测试和中文文档；`apps/website` 必须保持零差异。
