# 运动与表现同步的窄调整提案

日期：2026-09-06。状态：**待用户确认执行时序，尚未实施**。

依据：[现行角色规格](2026-09-05-ai-pet-custom-state-autonomy-design.md)第 6、8 节；真实证据见[Task 7 验收记录](../../operations/2026-09-06-custom-state-autonomy.md)。仅补运动情境的候选资格与执行时序，不替代整体角色设计。

## 已证实的问题

真实用户角色发布修复后，“播放运动状态”能播放跑步动画并约 3 秒回 idle；“向右走一点”也能实际完成 49 DIP 相对位移。但整段位移仍是 idle。“进入运动状态”的明确入口修复后仅播放动画，后续模型计划却继续选择跑步，观察期内未回 idle。当前 Main 在模型请求前启动短移动，模型选好动画时可能早已到达；表现计划也无法持续约束“仅在移动中适用”。

仅收到 `move-start` 或 `move-stop` 边沿不足以解决：它们只过滤已有候选；停止之后到达的计划仍可能重新播放跑步。不能给作者状态强加官方 `move` 语义，也不能根据名称本地猜选。

## 建议的共同调整

1. 保持唯一表现计划。状态候选和动作候选各增加可选 `whenMoving: boolean`，省略表示不限；它只表示真实移动事实，不表示作者的状态类别或任何运动权限。
2. Main 用当前 MotionService 的 `moving` 同时筛选状态和动作。移动开始、停止时立即重新检查资格；停止后不继续播放只适用于移动的候选。明确指定动画仍可以在原地播放跑步，不把动画反向转换为位移。
3. 同一模型请求根据现有人设、状态与动作描述提出条件候选。既有 `runtime.moving` 保持真实值；若 Main 已解析尚未执行的移动，额外传递有界的待执行意图标记，不能伪称已经移动。
4. 仍使用 DeepSeek／Qwen、原 Provider 与原有无工具聊天请求，不增逐帧或高频模型调用，不建立第二套语义映射或缓存引擎。

## 待确认的执行时序

推荐同步优先：已有合格运动表现计划时立即移动；没有计划时先等待同轮模型，接纳条件候选后启动原位移，靠真实移动边沿切动画。停止移动始终立即执行。

另一选择是保持立即移动：没有合格计划时先用当前表现或 idle，模型回包后按当时真实情境选择。这保留响应速度，但不能保证第一次短移动有对应动画。

同步优先需要复用 Director 现有唯一 pending 槽，保存 Main 已解析的精确请求、来源和轮次标记。相对方向与距离不再转换为区域目标；提交时先清槽，不能重复执行。新输入、停止、取消、拖拽、角色／Provider／配置变化、reset、close、转入文件任务或确认流程均清除待执行位移；迟到结果不恢复它。

建议无模型、无匹配或请求失败时保留已授权位移的降级能力，显示没有匹配动画的事实；取消与失效不触发降级。等待截止复用现有 Main 推进，建议上限 8 秒，到期仍未匹配则按所选降级策略处理，不创建额外后台循环。此参数和降级属于本提案，未记录为已获批或已实现。

## 修改与验收边界

预计只改角色计划 Schema／引擎、Main Service／Director／聊天适配与相应定向测试。作者角色包、人设和素材不需要迁移；锚点区域不扩展，MCP 禁用、文件授权、官网链均不变。

先写最小失败用例：移动中选择任意作者命名状态／动作、停止后排除该候选；停止后才抵达的旧运动建议不播放跑步；单状态多动作同样过滤；明确原地动作不移动；等待中的取消／停止／切换不会启动旧位移。实现后只复测这些边界及一次真实 UI 移动开始—动画切换—移动结束场景，不能用模型口头承诺作为执行证据。
